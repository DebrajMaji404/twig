Why "Twig"

Most compact formats flatten nested keys into a dotted path — address.district.village.block — repeated once per field. At real depth, that path gets longer than the value it's naming, and the format defeats its own purpose.

Twig instead treats nesting like an actual tree: every branch only needs to know its immediate parent, not the full path back to the root — the same way a twig doesn't need to know the whole tree it grows from, just the branch it's attached to.

A field then references only its own level. The full path is reconstructed by walking the tree backward. Schema cost per field stays constant, whether your data is nested 2 levels or 100.

@tree l1=address^- l2=present^l1 @types name l2.state l2.pin @rows ffs|West Bengal|713201

Note: Twig correctly distinguishes "field never present" from "field present but null" — for scalars, nested branches, array fields, and even empty-dict branches ({"x": {}}). This costs roughly 5 percentage points of compression (a presence flag written per array/branch per row) compared to a version without it — a deliberate trade-off, correctness by default. Install

MIT-licensed. Python 3.8+, zero dependencies.

# from a local clone pip install -e . # then in Python from twig import encode, decode text = encode(my_json) data = decode(text)

Twig is open source and not a novel invention — it combines tabular flattening, relational table-splitting, and a parent-pointer tree for nesting, tested extensively along the way (including bugs found and fixed in public, documented in the commit history). If you need a format with a larger community, look at TOON first.
